一、AIGC 全流程相关

请介绍一下你设计的 AIGC 全流程是怎么运转的？

AIGC 全流程覆盖 7 个环节，形成闭环：

  1. 需求触发：影刀 RPA 自动采集灵感图片入库，或设计师在中台/飞书手动触发生图
  2. 提示词工程：内置风格/品类/场景模板库，支持参数化组合，设计师可保存个人模板
  3. 模型调度：按场景智能调度——豆包 Vision（识别分类）→ MiniMax Embedding（向量化）→ 文生图大模型（二创出图）→ LLM（对话/分析）
  4. 内容生成：对接第三方异步生图 API，提交→轮询→结果聚合，支持 1-4 张并发批量生成
  5. 质量筛选：Vision 模型自动审核质量与合规性，设计师人工筛选确认
  6. 入库沉淀：自动下载转存对象存储，AI 打标签分类，文档自动切片→向量化
  7. 分发应用：二创中心展示、飞书推送、供应链报价关联、RAG 语义检索

业务数据回流形成迭代优化闭环，持续提升生成质量。

AIGC 全流程中最难的是哪一环？怎么解决的？

模型调度是最难的一环，核心挑战：

  • 响应时间差异大：Vision 秒级响应、生图 10-30 秒异步、Embedding 后台队列处理
  • 统一编排：不同模型的超时策略、重试机制、错误处理各不相同

解决方案：

  • 统一封装 ModelService 接口（input→output），每个模型实现统一接口
  • 异步生图用 CompletableFuture.supplyAsync() + join() 实现轮询，最多 120 秒超时
  • Vision 用同步调用，Embedding 走后台异步队列
  • 配置化管理 API Key/超时/重试，新增模型仅需配置密钥
提示词模板是怎么设计的？

采用三层结构：

  1. 基础描述层：固定的主体描述（如"一件连衣裙"）
  2. 风格修饰层：可选的风格标签（赛博朋克/极简/国潮/复古等）
  3. 技术参数层：尺寸比例（1:1/16:9/9:16）、质量参数

设计师可保存个人模板，下次一键复用。同时利用 ChatGPT、Claude 辅助调优提示词，提升生成质量。

怎么保证 AIGC 内容质量？

采用双重机制：

  • 自动审核：Vision 模型检测图片质量（清晰度、构图）与合规性（无违规内容），不合格标记为"待审核"
  • 人工筛选：设计师在二创中心浏览，只有确认的图片才入库并推送飞书

未通过审核的图片不进入知识库，保证沉淀内容的质量。

异步生图的轮询机制是怎么实现的？

第三方生图 API 是异步的，POST 提交后返回 {id, status: "running"}，需要轮询查询结果。

实现方式：

  • 使用 CompletableFuture.supplyAsync() 提交异步任务
  • 轮询接口：GET https://grsai.dakka.com.cn/v1/api/result?id={taskId}
  • 轮询间隔：每 3 秒查询一次，最多 120 秒超时
  • 状态判断：status: "succeeded" 时提取结果，"failed" 时抛出异常
  • 结果提取：extractAllImageUrls() 从 results/data/images 等多种格式提取所有图片 URL
踩坑记录：最初用 Future + TimeUnit 实现，Java 21 环境无法解析 TimeUnit，改用 CompletableFuture 后问题解决。
4 类模型怎么统一管理的？

统一封装 ModelService，每个模型实现统一接口：

  • 输入标准化：统一的 Input 对象（文本/图片/参数）
  • 输出标准化：统一的 Output 对象（文本/图片/向量/结构化数据）
  • 配置化管理：API Key、超时时间、重试次数、降级策略均通过配置文件管理
  • Coze 工作流编排：通过节点可视化编排调用顺序，无需改代码

新增模型接入仅需配置 API 密钥和实现接口，无需修改核心逻辑。

AIGC 流程的可观测性怎么做的？
  • 每个环节写入结构化日志（耗时/状态/模型版本），便于排查问题
  • 飞书通知包含环节名称 + 结果摘要，业务人员可感知流程进度
  • 中台管理后台可查看全链路执行记录，支持按时间/状态/用户筛选
  • 关键指标监控：生图成功率、平均耗时、模型调用次数

二、系统架构相关

为什么选择 Next.js + Spring Boot 的技术栈？

前端 Next.js 16：

  • App Router + React Server Components，首屏性能优秀
  • API Routes 可做 BFF 层，统一处理认证、降级、数据转换
  • shadcn/ui + Tailwind CSS 4，开发效率高，样式一致性好

后端 Spring Boot：

  • 企业级框架，生态成熟，JPA/Hibernate 简化数据库操作
  • PostgreSQL JSONB 支持半结构化数据，适合动态字段场景
  • Spring Security 提供完善的认证授权能力

前后端分离：前端通过 API Routes 代理后端请求，解决跨域、降级、数据转换问题。

前后端双模式架构是怎么设计的？

设计思路：后端不可用时，前端自动降级为 Mock 模式，保障核心功能可用。

实现方式：

  • 前端 isBackendAvailable() 检测后端可用性（30 秒缓存）
  • API Routes 层判断后端状态，不可用时返回 Mock 数据
  • 认证降级：后端不可用时，检查本地 Cookie 中的 session_id 即可通过验证
  • 数据降级：返回前端内置的 Mock 数据展示

效果：核心功能可用率 99%+，后端故障时用户仍可浏览、搜索、预览。

动态数据模型引擎是怎么设计的？

核心思路：PostgreSQL 主表 + JSONB 扩展字段，前端 FieldDef 驱动渲染。

后端：

  • 主表存储通用字段（id, name, created_at 等）
  • JSONB 字段存储动态字段数据
  • JdbcTemplate 返回 PGobject，需 ObjectMapper 手动解析为 Map

前端：

  • FieldDef 定义字段类型（文本/数值/日期/多选等）、排序、是否可见
  • 表格列、表单输入、单元格渲染完全由 FieldDef 驱动生成
  • 新增业务实体只需配置字段，无需建表/写接口/写页面
踩坑记录：PGobject 默认不在 classpath（postgresql 依赖 scope=runtime），改为 compile 后编译通过。
RBAC 多租户数据隔离是怎么实现的？

权限模型：角色（admin/user）+ 公司维度，行级数据隔离。

实现方式：

  • SessionUtil 获取当前用户角色、公司、用户 ID
  • JPA Criteria 动态拼接权限谓词：
// 管理员：看同公司所有用户的数据 if (isAdmin) { predicates.add(cb.equal(root.get("company"), currentCompany)); } // 普通用户：只看自己的数据 else { predicates.add(cb.equal(root.get("company"), currentCompany)); predicates.add(cb.equal(root.get("userId"), currentUserId)); }

效果：管理员可管理同公司所有数据，普通用户仅可见个人数据，数据完全隔离。

供应链智能报价模块是怎么实现的？

核心逻辑：

  • 原料用量 × 采购最低价 = 单项成本
  • 汇总所有原料成本 = 总成本
  • 总成本 × 利润率 = 建议报价

供应商对比：

  • 按原料编码聚合所有供应商报价
  • 输出最低价/最高价/节省比例对比视图
  • 自动标记最优供应商

效果：报价计算从人工核算 2 小时降至一键出结果，原料采购成本平均降低 8-15%。

系统的安全性是怎么保障的？
  • 认证安全：Session ID 使用 crypto.randomUUID() 生成，支持自动续期，每用户最多 5 个并发 Session
  • CSRF 保护：验证 Origin/Referer，Cookie 仅限 HTTP 传输
  • 输入验证：Zod Schema 校验，防止 SQL 注入和路径遍历
  • 速率限制：登录 5 分钟 5 次，上传 1 分钟 20 次，改密 1 小时 3 次
  • 安全头：X-Frame-Options、X-Content-Type-Options、X-XSS-Protection 等
  • 日志脱敏：自动过滤 password、token、secret 等敏感字段

三、前端技术相关

Next.js 16 的 App Router 相比 Pages Router 有什么优势？
  • React Server Components：默认服务端渲染，减少客户端 JS 体积
  • 流式渲染：Suspense + streaming，首屏更快
  • 嵌套布局：layout.tsx 支持嵌套，共享 UI 不重新渲染
  • 数据获取：直接在组件中 async/await，无需 getServerSideProps
  • 路由分组：(group) 语法组织路由，不影响 URL 结构
动态字段驱动的表格是怎么实现的？

核心思路：表格列、表单、单元格渲染完全由 FieldDef 定义决定，不写死。

实现步骤：

  1. 后端返回 FieldDef 数组（字段名、类型、排序、是否可见）
  2. 前端根据 FieldDef 动态生成表格列配置
  3. 单元格渲染根据字段类型选择组件（文本/数值/日期/多选等）
  4. 表单输入同样根据 FieldDef 动态生成
关键代码：renderCellValue(field, value) 根据 field.type 返回对应渲染组件。
图片下载 500 错误是怎么排查和修复的？

问题现象：点击下载报 500 "服务器内部错误"。

排查过程：

  1. 查看日志发现 ECONNREFUSED，后端 Java 服务不可用
  2. file/route.ts 的 backendFetch 获取详情失败，catch 返回 500

修复方案：

  • backendFetch 失败不再直接抛异常，改为 try/catch 降级处理
  • 主 URL 获取失败时自动尝试 originalUrl 降级
  • 支持 /api/uploads/ 前缀的后端路径拼接
  • 前端增加 502/504 友好提示"后端服务不可用"
shadcn/ui 和传统 UI 库有什么区别？
  • 不是 npm 包：直接复制组件代码到项目，完全可控
  • 基于 Radix UI：无样式的基础组件，可访问性好
  • Tailwind CSS 样式：样式与逻辑分离，易于定制
  • 零运行时开销：编译时确定，无额外 JS 体积
前端是怎么处理跨域的？

方案：Next.js API Routes 做 BFF 层代理。

  • 前端请求 /api/xxx，API Routes 转发到后端 http://localhost:8080/api/xxx
  • 服务端转发无跨域问题，同时可处理认证、降级、数据转换
  • 图片代理：/api/uploads/[[...path]] 转发静态资源请求
无限滚动是怎么实现的？

实现方式：

  • 后端支持分页参数（page, pageSize, cursor）
  • 前端监听滚动事件，距离底部 200px 时触发加载
  • 使用 IntersectionObserver 检测加载哨兵元素
  • 加载时显示骨架屏，防止重复请求

优化：防抖处理、请求去重、错误重试。

Tailwind CSS 4 相比之前版本有什么变化？
  • OKLCH 色彩空间：更均匀的颜色感知
  • CSS-first 配置：用 CSS 变量替代 tailwind.config.js
  • 更快的构建：基于 Rust 的引擎，构建速度提升 10x
  • 自动内容检测：无需配置 content 路径
前端是怎么做错误监控的？
  • 统一错误边界：React Error Boundary 捕获组件渲染错误
  • API 错误处理：统一封装 fetch 请求，捕获网络错误和业务错误
  • Toast 提示：使用 sonner 库展示用户友好的错误信息
  • 日志上报：关键错误写入 /app/work/logs/bypass/console.log

四、后端技术相关

Spring Boot 中 JPA 和 JdbcTemplate 有什么区别？为什么都用？
  • JPA/Hibernate：ORM 框架，适合标准 CRUD，代码简洁，支持复杂查询（Specification）
  • JdbcTemplate：轻量级，适合动态 SQL、批量操作、JSONB 字段处理

使用场景：

  • 主表查询用 JPA（动态表、权限过滤）
  • 动态表查询用 JdbcTemplate（字段不固定，需动态拼接 SQL）
  • JSONB 字段解析用 JdbcTemplate（PGobject 需手动处理）
JSONB 字段的 PGobject 解析问题是怎么解决的？

问题：JdbcTemplate 查询 JSONB 字段返回 PGobject，无法直接转为 Map。

解决：

  1. 添加 postgresql 依赖，scope 从 runtime 改为 compile（解决编译期 PGobject 不可见）
  2. 编写 parseJsonbFields() 方法，用 ObjectMapper 将 PGobject 解析为 Map
private void parseJsonbFields(Map<String, Object> row, String... fieldNames) { for (String fieldName : fieldNames) { Object value = row.get(fieldName); if (value instanceof PGobject) { String json = ((PGobject) value).getValue(); row.put(fieldName, objectMapper.readValue(json, Map.class)); } } }
CompletableFuture 和 Future + TimeUnit 有什么区别？
  • Future + TimeUnit：阻塞式等待，需要 TimeUnit 类（Java 21 环境无法解析）
  • CompletableFuture：非阻塞式，支持链式调用、组合、回调

选择原因：

  • Java 21 环境无法解析 TimeUnit，编译报错
  • CompletableFuture 更现代，支持 supplyAsync() + join()
  • 代码更简洁，可读性更好
Session 管理是怎么实现的？
  • Session ID 生成：使用 crypto.randomUUID() 生成不可预测的 ID
  • Session 存储：内存 Map 存储（生产环境可改为 Redis）
  • Session 续期：每次请求自动续期，避免频繁登录
  • 并发限制：每用户最多 5 个并发 Session，超出则淘汰最早的
  • 自动清理：定时任务清理过期 Session
速率限制是怎么实现的？

实现方式：基于内存的滑动窗口计数器。

  • 不同操作配置不同限流策略：登录 5 分钟 5 次，上传 1 分钟 20 次
  • 使用 ConcurrentHashMap 存储请求记录
  • 每次请求检查窗口内请求数，超出则拒绝
  • 定时清理过期记录，防止内存泄漏

效果：防止恶意刷接口，保障系统稳定性。

Spring Boot 的自动配置原理是什么？
  • @SpringBootApplication：包含 @EnableAutoConfiguration
  • META-INF/spring.factories：声明自动配置类
  • 条件注解：@ConditionalOnClass、@ConditionalOnMissingBean 等控制配置生效
  • 配置优先级：用户自定义配置 > 自动配置
JPA Criteria 动态查询是怎么实现的？

核心思路：根据请求参数动态拼接 Predicate 列表。

Specification<Image> spec = (root, query, cb) -> { List<Predicate> predicates = new ArrayList<>(); // 基础条件 predicates.add(cb.equal(root.get("deleted"), false)); // 动态条件 if (company != null) { predicates.add(cb.equal(root.get("company"), company)); } if (userId != null && !isAdmin) { predicates.add(cb.equal(root.get("userId"), userId)); } return cb.and(predicates.toArray(new Predicate[0])); };

优势：类型安全、可组合、易于测试。

Spring Security 的认证流程是什么？
  1. 请求进入 SecurityFilterChain
  2. AuthenticationFilter 提取凭证（Session ID）
  3. AuthenticationProvider 验证凭证
  4. 验证成功则设置 SecurityContext，继续处理请求
  5. 验证失败则返回 401

五、数据库相关

为什么选择 PostgreSQL 而不是 MySQL？
  • JSONB 支持：原生支持 JSONB 类型，适合动态字段场景
  • 向量检索：pgvector 扩展支持向量存储与检索，适合 RAG 场景
  • 全文搜索：内置全文搜索能力
  • 扩展性：支持自定义类型、函数、索引
JSONB 和 JSON 有什么区别？
  • JSON：存储原始 JSON 文本，每次查询需解析
  • JSONB：二进制格式，存储时解析，查询更快
  • 索引支持：JSONB 支持 GIN 索引，可高效查询嵌套字段
  • 操作符：JSONB 支持 @>、?、?| 等操作符

选择：动态字段场景用 JSONB，查询性能更好。

向量检索是怎么实现的？

技术栈：pgvector 扩展 + MiniMax Embedding。

流程：

  1. 文档上传后自动切片（800 字符/片，100 字符重叠）
  2. 调用 MiniMax Embedding API 获取向量（1536 维）
  3. 存入 knowledge_embeddings 表（vector 类型）
  4. 查询时计算余弦相似度，返回 Top-K 结果
SELECT * FROM knowledge_embeddings ORDER BY embedding <=> $1::vector LIMIT 5;
数据库表是怎么设计的？

核心表：

  • users：用户表（id, username, password, role, company）
  • images：主图片表（id, url, title, user_id, company, source）
  • albums：相册表（id, name, user_id）
  • knowledge_base_docs：知识库文档表（id, title, content, embedding_status）
  • knowledge_embeddings：向量嵌入表（id, content, embedding, source_type）

设计原则：主表 + JSONB 扩展，兼顾标准化与灵活性。

数据库迁移是怎么管理的？
  • 使用 Flyway 管理数据库版本
  • 迁移脚本放在 db/migration/ 目录
  • 命名规范：V{version}__{description}.sql
  • 启动时自动执行未应用的迁移

六、AI 模型集成相关

豆包 Vision 是怎么集成的？

使用场景：图片智能识别与自动分类。

集成方式：

  1. 上传图片 Base64 编码
  2. 调用豆包 Vision API，传入提示词（如"识别这张图片的风格、品类、场景"）
  3. 解析返回结果，提取标签
  4. 自动为图片打标签，存入数据库

效果：自动分类准确率 85%+，减少人工标注工作量。

MiniMax Embedding 是怎么用的？

使用场景：文档向量化，支持 RAG 语义检索。

流程：

  1. 文档上传后提取文本内容
  2. 按 800 字符切片，100 字符重叠
  3. 调用 MiniMax Embedding API 获取 1536 维向量
  4. 存入 knowledge_embeddings 表

检索：查询时计算余弦相似度，返回 Top-K 相关片段。

RAG 语义检索是怎么实现的？

RAG（Retrieval-Augmented Generation）：检索增强生成。

实现步骤：

  1. 索引阶段：文档切片→向量化→存入向量数据库
  2. 检索阶段：用户查询→向量化→余弦相似度匹配→返回 Top-K 片段
  3. 生成阶段：将检索结果作为上下文，调用 LLM 生成回答
// 伪代码 query_embedding = embed(query_text) results = vector_db.search(query_embedding, top_k=5) context = "\n".join([r.content for r in results]) answer = llm.generate(context + "\n\n问题：" + query_text)

效果：检索命中率从 30% 提升至 80%+。

文生图大模型是怎么对接的？

对接流程：

  1. POST 提交生图任务（prompt, size, count）
  2. 返回 {id, status: "running"}
  3. 轮询查询结果：GET /result?id={taskId}
  4. 状态为 "succeeded" 时提取图片 URL
  5. 下载图片到本地对象存储

优化：支持 1-4 张并发生成，用户可选数量。

LLM 智能对话是怎么实现的？

实现方式：

  • 基于 RAG 检索的知识库上下文
  • 调用 LLM API（如豆包、Kimi）生成回答
  • 支持多轮对话，记忆上下文
  • 流式输出，打字机效果

应用场景：智能客服、知识问答、报价分析。

AI 模型的调用成本怎么控制？
  • 缓存：相同查询直接返回缓存结果
  • 批量处理：合并多个请求，减少 API 调用次数
  • 降级策略：模型不可用时返回默认结果
  • 限流：限制单用户调用频率

七、影刀 RPA 相关

影刀 RPA 采集流程是怎么编排的？

流程设计：

  1. 定时触发：每天凌晨 2 点自动执行
  2. 网站爬取：访问时尚网站，提取图片 URL 和描述
  3. 图片下载：批量下载图片到本地
  4. 数据清洗：去重、过滤低质量图片
  5. API 导入：调用中台 API 批量入库
  6. 结果通知：飞书群消息通知采集结果

效果：日采集量 500+ 张，效率提升 10 倍+。

采集的图片怎么去重？

去重策略：

  • URL 去重：相同 URL 直接跳过
  • 感知哈希（pHash）：计算图片哈希值，相似度 > 90% 视为重复
  • 入库前检查：查询数据库是否已存在相同图片
RPA 采集失败怎么处理？
  • 重试机制：失败后自动重试 3 次
  • 错误日志：记录失败原因和 URL
  • 告警通知：连续失败 5 次发送飞书告警
  • 断点续传：记录已采集位置，下次从断点继续
RPA 采集的合规性怎么保证？
  • robots.txt：遵守网站爬虫协议
  • 请求频率：控制爬取速度，避免对目标网站造成压力
  • 版权过滤：过滤明显有版权保护的内容
  • 仅供内部使用：采集的图片仅用于内部灵感参考，不对外发布

八、Coze + 飞书集成相关

Coze 工作流是怎么编排的？

工作流节点：

  1. 触发节点：RPA 采集完成 / 飞书机器人对话
  2. 图片分类节点：调用 Vision API 识别风格/品类
  3. 条件分支：根据分类结果选择不同处理逻辑
  4. 生图节点：调用文生图 API 生成二创图片
  5. 存储回写节点：下载图片并入库
  6. 飞书通知节点：推送结果到飞书群

优势：可视化编排，无需改代码即可调整流程。

飞书机器人是怎么对接的？

对接方式：

  • 事件订阅：监听用户 @ 机器人事件
  • 消息卡片：富文本展示结果，支持交互按钮
  • Webhook：接收 Coze 工作流回调，推送消息

功能：设计师通过飞书对话直接触发生图，无需登录中台。

飞书审批流是怎么实现的？

实现步骤：

  1. 中台创建审批实例（报价/采购申请）
  2. 调用飞书审批 API 创建审批单
  3. 审批人在飞书内审批
  4. 审批完成后回调中台，更新状态

效果：审批周期从 3-5 天缩短至当天。

Coze 智能体 Bot 是怎么配置的？
  • 人设与回复逻辑：配置系统提示词，定义角色和回复风格
  • 知识库：关联中台知识库，支持 RAG 检索
  • 插件：添加生图、查询等插件能力
  • 工作流：编排复杂业务流程
飞书集成的难点是什么？
  • 事件回调验证：需要验证签名，防止伪造请求
  • 权限申请：飞书开放平台权限申请流程较长
  • 消息卡片交互：需处理双向回调，逻辑复杂
  • 审批流对接：审批状态同步需处理回调延迟

九、OpenClaw 相关

OpenClaw 是什么？

OpenClaw 是一个 AI Skill 生态平台，支持安装、开发、调用 AI 能力（Skill）。

Skill：封装的 AI 能力单元，如图片处理、文本生成、数据转换等。

Skill 是怎么安装的？

安装方式：

  1. 从 Skill 市场选择需要的 Skill
  2. 点击安装，自动下载到本地 skills/ 目录
  3. 配置 API Key 等参数
  4. 即可在代码中调用
自定义 Skill 是怎么开发的？

目录结构：

my-skill/ ├── skill.yaml # Skill 配置（名称、描述、输入输出） ├── main.py # 核心逻辑 ├── requirements.txt # 依赖 └── README.md # 使用说明

开发步骤：

  1. 定义输入输出接口契约
  2. 实现核心逻辑
  3. 编写单元测试
  4. 发布到 Skill 市场（可选）
你开发了哪些 Skill？
  • 图片批量处理：批量缩放、裁剪、格式转换
  • Prompt 模板管理：保存、加载、组合提示词模板
  • 模型结果解析：统一解析不同模型的返回格式
  • 数据格式转换：JSON/CSV/Excel 互转

十、性能优化相关

前端性能是怎么优化的？
  • 首屏优化：React Server Components 减少客户端 JS 体积
  • 图片优化：Next.js Image 组件自动懒加载、格式转换
  • 代码分割：动态 import 按需加载
  • 缓存策略：静态资源长期缓存，API 数据短期缓存
  • 虚拟滚动：长列表只渲染可视区域
后端性能是怎么优化的？
  • 数据库索引：为常用查询字段添加索引
  • 连接池：HikariCP 连接池，减少连接开销
  • 缓存：Redis 缓存热点数据
  • 异步处理：耗时操作（如向量化）走异步队列
  • 分页查询：避免一次性加载大量数据
无限滚动的性能问题怎么解决？
  • 防抖：滚动事件 200ms 防抖
  • 请求去重：加载中状态阻止重复请求
  • 错误重试：失败后自动重试 3 次
  • 骨架屏：加载时显示占位，避免布局抖动
大量图片上传怎么优化？
  • 分片上传：大文件分片，支持断点续传
  • 并发控制：限制同时上传数量（如 3 个）
  • 进度显示：实时显示上传进度
  • 失败重试：单个文件失败不影响其他文件
  • 压缩：前端压缩图片后再上传
怎么排查性能问题？
  • 前端：Chrome DevTools Performance 面板分析渲染性能
  • 后端：日志记录耗时，定位慢查询
  • 数据库：慢查询日志、EXPLAIN 分析执行计划
  • 监控：APM 工具（如 SkyWalking）监控全链路性能

十一、项目管理与独立开发相关

一个人怎么完成这么多功能的？

关键策略：

  • 技术选型：选择成熟框架（Next.js、Spring Boot），减少踩坑
  • AI 辅助：熟练使用 ChatGPT、Claude 辅助编码，效率提升 3 倍+
  • 模块化设计：统一封装中间件、Service，新增功能复用已有代码
  • 优先级管理：先实现核心功能，再迭代优化
  • 前后端分离：并行开发，联调零成本

效果：一人完成全栈开发，迭代速度比多人分工更快。

遇到技术难题怎么解决？

解决思路：

  1. 分析问题：拆解问题，定位根因
  2. 搜索资料：官方文档、Stack Overflow、GitHub Issues
  3. AI 辅助：ChatGPT/Claude 提供解决方案
  4. 最小复现：写最小 demo 验证方案
  5. 记录总结：踩坑记录，避免重复犯错
怎么保证代码质量？
  • 代码规范：ESLint、Prettier 统一风格
  • 类型安全：TypeScript 严格模式
  • 单元测试：核心逻辑编写测试
  • 代码审查：自己 review 自己的代码（独立开发的无奈）
  • 持续集成：提交前自动运行 lint、test
项目是怎么规划的？

规划方式：

  • 需求分析：梳理核心功能，划分优先级
  • 技术设计：画架构图、数据库设计、接口设计
  • 迭代开发：按功能模块迭代，每迭代交付可用版本
  • 测试验收：每个功能自测通过后提交
独立开发有什么优缺点？

优点：

  • 决策快，无需沟通成本
  • 前后端一人掌控，联调零成本
  • 问题定位快，全链路可见

缺点：

  • 单点故障，请假项目停摆
  • 缺乏代码审查，可能有盲区
  • 压力大，需全栈能力
如果给你更多时间，会怎么优化？
  • 微服务化：拆分为独立服务（用户服务、图片服务、AI 服务）
  • 消息队列：异步任务走 MQ（如 RabbitMQ），解耦
  • 容器化：Docker + K8s 部署，弹性伸缩
  • 监控告警：完善 APM、日志、告警体系
  • 多租户：支持 SaaS 化，多公司数据隔离
